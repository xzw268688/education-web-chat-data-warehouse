## 3.1 业务背景与分析问题

### 3.1.1 业务背景

本项目的业务对象是一家教育机构的官方网站。官网承担两条核心职能：一是通过课程页面承接搜索引擎、站内入口和其他网站的访问流量；二是通过在线客服把访问者转化为咨询线索。访客从进入官网开始，会产生浏览页面、发起咨询、与客服对话等一系列行为，这些行为被客服系统记录在 MySQL 的两张业务表中。

随着投放渠道增多，运营团队面临一个现实问题：**流量看起来不少，但说不清哪些流量真正带来了咨询**。现有数据分散在“访问会话表”和“页面信息表”中，缺少统一的分层汇总和明确的口径，运营只能凭经验判断渠道优劣，客服主管也无法量化响应效率。

本项目把这两张源表加工成 ODS / DWD / DWS 三层数据仓库，把“访问—咨询—响应—有效沟通”的链路拆开，用统一口径回答经营问题，并通过 FineBI 形成可日常查看的看板。

### 3.1.2 当前业务痛点

1. **流量与咨询割裂**：访问会话与页面信息分表存储，无法直接判断哪些渠道、地区、页面带来的咨询更多。
2. **统计口径不统一**：会话数、用户数、IP 数三种口径混用，不同人算出的“咨询率”对不上。
3. **维度不完整**：地区、渠道、页面、设备、时段没有统一汇总，缺少多维对比。
4. **过程不可核验**：从源库到报表之间没有逐层对账，指标出错时无法定位是哪一层的问题。

### 3.1.3 要回答的四个业务问题

| 编号 | 分析问题 | 对应指标 |
|---|---|---|
| Q1 | 官网流量规模有多大，来自哪些地区、渠道、页面、设备和时段？ | 会话总量、UV、地区/渠道/页面/设备/时段分布 |
| Q2 | 访问中有多少转化为咨询，整体咨询率是多少？ | 咨询会话数、咨询用户数、三口径咨询率 |
| Q3 | 不同渠道、不同地区的咨询转化差异有多大？ | 分渠道咨询率、分地区咨询率 |
| Q4 | 咨询之后客服是否响应，用户是否形成有效沟通，流失在哪一步？ | 客服响应率、高意向会话数、四段转化漏斗 |

### 3.1.4 指标使用者与业务价值

| 使用者 | 关心的问题 | 使用的指标 |
|---|---|---|
| 市场/投放 | 哪个渠道带来高质量流量，预算该往哪投 | 渠道访问量、渠道咨询率、高意向会话数 |
| 运营 | 哪些地区、页面、时段是流量高峰 | 地区访问量、页面排行、时段分布 |
| 客服主管 | 客服是否及时响应，接待质量如何 | 客服响应率、有效沟通数、漏斗转化率 |
| 管理层 | 整体获客效率是否健康 | 会话总量、UV、三口径咨询率、日趋势 |

### 3.1.5 范围与边界

- **时间范围**：仅 2025 年 7 月，单月数据，不做跨月环比。
- **数据范围**：仅使用 `nev` 库的两张表，不引入订单、营收等外部数据。
- **分析边界**：到“咨询/响应/有效沟通”为止，不涉及成单金额和成交归因。
- **实时性**：离线日批，不做实时流处理。
- **未知值处理**：地区、渠道、浏览器为空时统一归一为“未知”，保留在分析中，不直接删除。

## 3.2 业务指标清单

### 3.2.1 口径约定

| 术语 | 定义 |
|---|---|
| 访问会话 | `web_chat_ems` 中的一行，由 `session_id` 与 `create_time` 共同标识；同一 `session_id` 在不同日期视为不同快照 |
| 访客 | 以 `sid` 去重的用户；同一访客可产生多次会话 |
| 咨询会话 | `msg_count > 0` 的访问会话，即用户至少发送过一条消息 |
| 咨询用户 | 咨询会话中 `sid` 去重后的数量 |
| 客服响应 | 咨询会话中 `reply_msg_count > 0`，即客服至少回复过一条消息 |
| 高意向会话 | `msg_count >= 9` 的咨询会话；9 为本月咨询会话 `msg_count` 的 P75（P50=6、P75=9、P90=12） |
| 有效沟通 | `msg_count >= 9` 且 `reply_msg_count > 0` 的咨询会话 |
| 转化漏斗 | 访问会话 → 咨询会话 → 客服响应 → 有效沟通 四段 |
| 未知值 | 源字段为空或为占位符时统一记为“未知” |

**比率计算约定**：所有比率保留 4 位小数，以百分比展示；分母为 0 时返回 0，不返回空值。

### 3.2.2 指标清单（15 个）

| # | 指标 | 域 | 计算逻辑 | 粒度 | 业务用途 |
|---|---|---|---|---|---|
| 1 | 会话总量 | 流量 | `COUNT(DISTINCT session_id)` | 日 / 月 | 衡量官网访问规模 |
| 2 | 独立访客数 UV | 流量 | `COUNT(DISTINCT sid)` | 日 / 月 | 衡量真实到访人数 |
| 3 | 日均会话数 | 流量 | 会话总量 ÷ 有数据天数 | 月 | 排除天数差异后的规模对比 |
| 4 | 地区访问会话量 | 流量 | `COUNT(DISTINCT session_id) GROUP BY country, province, city` | 日 + 地区 | 识别流量来源地区 |
| 5 | 渠道访问会话量及占比 | 流量 | 按 `origin_channel`、`seo_source` 分组计数；占比 = 组内会话数 ÷ 当日总会话数 | 日 + 渠道 | 评估渠道结构 |
| 6 | 页面访问排行 | 流量 | 按 `url_title` 分组计数并降序排名，取 TopN | 日 + 页面 | 识别热门课程页 |
| 7 | 设备分布 | 流量 | 按 `os_info`、`browser_name` 分组计数 | 日 + 设备 | 判断用户终端结构 |
| 8 | 时段分布 | 流量 | 按 `HOUR(create_time)` 分组计数 | 日 + 小时 | 识别咨询高峰时段 |
| 9 | 咨询会话数 | 转化 | `COUNT(DISTINCT session_id) WHERE msg_count > 0` | 日 / 月 | 衡量咨询规模 |
| 10 | 咨询用户数 | 转化 | `COUNT(DISTINCT sid) WHERE msg_count > 0` | 日 / 月 | 衡量咨询人数 |
| 11 | 咨询率（三口径） | 转化 | 会话口径 = 咨询会话数 ÷ 访问会话数；用户口径 = 咨询用户数 ÷ UV；IP 口径 = 咨询 IP 数 ÷ 访问 IP 数 | 日 / 月 | 从三个角度衡量转化效率 |
| 12 | 分维度咨询率 | 转化 | 按渠道或地区分组的咨询会话数 ÷ 同组访问会话数 | 日 + 渠道/地区 | 找出高转化渠道与地区 |
| 13 | 高意向会话数 | 转化 | `COUNT(DISTINCT session_id) WHERE msg_count >= 9` | 日 / 月 | 识别高价值咨询 |
| 14 | 客服响应率 | 转化 | 客服响应会话数 ÷ 咨询会话数 | 日 / 月 | 衡量客服接待覆盖 |
| 15 | 四段漏斗转化率 | 转化 | 访问会话数 → 咨询会话数 → 客服响应数 → 有效沟通数；逐段转化率 = 后一段 ÷ 前一段 | 日 / 月 | 定位链路流失环节 |

### 3.2.3 指标与业务问题的对应

- Q1 → 指标 1–8
- Q2 → 指标 9–11
- Q3 → 指标 12
- Q4 → 指标 13–15

### 3.3.2 `web_chat_ems_2025_07`（访问会话表）

**业务含义**：记录官网客服系统中的访问会话。每一行代表一次独立会话，包含访客身份、进入时间、来源渠道、地区、客服接待过程、消息数量与设备信息，是流量与转化分析的主表。

**主键与关联**：`id` 为主键；`session_id` 为会话业务唯一键；`web_chat_text_ems_2025_07.id` 与本表 `id` 一对一关联。

### 3.3.5 源数据质量问题与清洗映射

| 问题 | 典型表现 | 处理方式 | 影响 |
|---|---|---|---|
| 会话或访客标识缺失 | `session_id` 或 `sid` 为空 | 剔除，不计入 DWD | 避免虚增会话/用户 |
| 时间缺失或非法 | `create_time` 为空或无法解析 | 剔除 | 无法归属日期分区 |
| 同一会话跨日快照 | 同一 `session_id` 在 07-01 与 07-25 各出现一次，除 `id`/日期外字段一致 | 按 `(session_id, create_time)` 标识，保留两个快照日；仅同日重复才剔除 | 避免把 07-25 快照误删 |
| 地区为空 | `country/province/city` 为空 | 归一为“未知”，保留 | 保留流量总量 |
| 渠道为空 | `origin_channel` / `seo_source` 为空 | 归一为“未知”，保留 | 渠道分析仍有完整分母 |
| 浏览器/系统为空 | `browser_name` / `os_info` 为空 | 归一为“未知”，保留 | 设备分布完整 |
| 文本超长 | 页面标题、URL、扩展字段过长 | 按目标字段长度截断 | 防止导出/入库截断报错 |
| 消息数为负 | `msg_count < 0` | 置为 0 | 保证指标合理 |
| 中文编码 | 导入后出现乱码 | UTF-8 连接 + utf8mb4 目标表 | 保证地区/渠道可读 |

+---------------------------+

### 3.4.2 每层的数据定位、存储作用与数据边界

| 层级 | 数据定位 | 存储作用 | 数据边界 |
|---|---|---|---|
| ODS | 源数据的镜像层 | 原样保留源表字段与取值，按天分区，便于回溯与重跑 | 到“原始会话记录”为止；不做清洗、不做聚合、不改变字段含义 |
| DWD | 明细与维度层 | 存储清洗后的会话事实和公共维度，采用星型模型，供 DWS 复用 | 到“一个会话一行”为止；不做跨维度指标聚合 |
| DWS | 汇总指标层 | 按日概览、地区、渠道、页面、设备时段五个场景存储聚合指标 | 到“日 + 维度组合”为止；不保留明细，不回写 DWD |
| 结果层 | 可视化服务层 | MySQL `edu_result` 存储与 DWS 同构的结果表，供 FineBI 直连 | 只读服务；不承担计算 |

**分层原则**：

1. 下层只向上层提供数据，上层不反向依赖下层明细。
2. 清洗只发生在 ODS→DWD，DWS 不再重复清洗。
3. 指标只在 DWS 计算，DWD 不提前聚合，避免口径分散。
4. 每层保留 `dt` 分区，保证同一日期可重跑、可对比。

### 3.4.3 命名与存储规范

| 规范 | 内容 |
|---|---|
| 数据库 | `edu_ods` / `edu_dwd` / `edu_dws` |
| 表名前缀 | ODS `ods_`；DWD 维表 `dim_`、事实表 `fact_`；DWS `dws_` |
| 存储格式 | 正式表统一 ORC；Sqoop 导入/导出使用 text 临时表 |
| 分区 | 正式表按 `dt=YYYY-MM-DD` 日分区；维表按日做快照 |
| 分隔符 | text 临时表以 `\t` 分隔；ORC 正式表无分隔符概念 |
| 压缩 | Hive `hive.exec.orc.compression.strategy=COMPRESSION` |

## 3.5 全层级数据表设计

### 3.5.1 ODS 层（2 张表）

#### 表 1：`edu_ods.ods_web_chat_ems`

- **业务作用**：保存访问会话源数据，作为全部流量与转化指标的原始依据。
- **存储内容**：与 MySQL `web_chat_ems_2025_07` 字段一一对应，新增 `dt` 分区。

## 3.6 数据流转流程

### 3.6.1 全链路流程图

> 正式提交时替换为 draw.io 导出的高清 PNG；源文件为 `docs/架构与流程图.drawio`。

```text
[MySQL nev]
   |  ① Sqoop import（UTF-8, \t, 全量）
   v
[HDFS /tmp/sqoop/*]
   |  ② LOAD DATA 到 text 临时表
   v
[text 临时表]
   |  ③ INSERT OVERWRITE ... PARTITION(dt)
   v
[ODS ORC 正式表]  -- 校验：行数 = 源表行数
   |  ④ 清洗 + 去重 + 归一化
   |  ⑤ 抽取 5 张维表
   |  ⑥ 关联维表生成 fact_visit / fact_consult
   v
[DWD 星型模型]    -- 校验：清洗后 211,197 行，保留 07-01/07-02/07-25 快照
   |  ⑦ 五个场景聚合
   v
[DWS 5 张聚合表]  -- 校验：分组合计 = 事实总数
   |  ⑧ 写入 text 中转表
   v
[DWS text 中转表]
   |  ⑨ Sqoop export（先按 dt 删除）
   v
[MySQL edu_result] -- 校验：导出行数 = DWS 行数
   |  ⑩ JDBC 数据连接
   v
[FineBI 三个看板]
```

### 3.6.2 流程节点说明与校验点

| 节点 | 输入 | 输出 | 校验点 |
|---|---|---|---|
| ① Sqoop 导入 | MySQL 两张源表 | HDFS text 文件 | 命令退出码为 0；UTF-8 参数生效 |
| ② 加载临时表 | HDFS text 文件 | text 临时表 | 行数与文件行数一致 |
| ③ 写入 ODS | text 临时表 | ODS ORC 分区 | 行数 = 源表行数；中文无乱码 |
| ④ DWD 清洗 | ODS | 清洗后会话快照 | 业务键 `(session_id, create_time)` 唯一；未知值保留 |
| ⑤ 维度抽取 | 清洗后会话 | 5 张维表 | 维表业务键唯一 |
| ⑥ 事实构建 | 清洗后会话 + 维表 | 2 张事实表 | 会话粒度唯一；外键全部匹配 |
| ⑦ DWS 聚合 | 事实表 | 5 张聚合表 | 分组合计 = 事实总数；比率在 0–100% |
| ⑧ 导出中转 | DWS ORC | text 中转表 | 行数一致 |
| ⑨ Sqoop 导出 | text 中转表 | MySQL 结果表 | 行数一致；无截断、无错位 |
| ⑩ BI 连接 | MySQL 结果表 | 三个看板 | 连接测试成功；图表可筛选 |

### 3.6.3 逐层对账口径

1. **源表 → ODS**：`COUNT(*)` 相等。
2. **ODS → DWD**：`fact_visit` 行数（按 `(session_id, create_time)` 快照）= ODS 行数；同日重复与无效记录的剔除量单独记录。
3. **DWD → DWS**：五张 DWS 表按 `dt` 的会话合计 = `fact_visit` 当日行数。
4. **DWS → MySQL**：每张结果表行数 = 对应 DWS 分区行数。
